# 碼率控制：壅塞證據與恢復

本次針對 log-41 顯示低輸出、但沒有目標碼率或佇列決策資訊的情況改善。日誌本身不能證明低輸出由 ABR 造成，亦不能確認 App 是否使用內建策略。

## 判斷

- 移除「三次佇列連續增加」的獨立降速入口。
- 佇列至少 128 KiB，且估算排空時間至少 0.75 秒，連續兩次採樣才送出頻寬不足事件。
- 排空時間使用當次送出速率與 EMA 的較大值，避免靜態來源恢復時，滯後的低 EMA 誤判壅塞。持續低吞吐仍會隨 EMA 收斂而觸發；短暫壅塞的反應可能較慢。
- 速率依實際單調時鐘間隔計算。送出量只代表觀測流量，不代表網路容量。

## 恢復

- 冷卻期間略過的重複事件不清除既有恢復進度；可執行的降速事件仍清除進度。
- 尚有超過大小與時間雙門檻的佇列時，status 不增加恢復計數。
- 保留原有單次非零吞吐最多降 25%、零吞吐砍半、最低為設定上限 20% 的限制。
- 保留六個可恢復 status 後增加上限 20% 的階梯。健康樣本可以跨越冷卻略過的事件，並非嚴格連續六秒。
- 重連使用最近經恢復窗口驗證的目標，避免回到歷史最低值；剛探升但尚未驗證的階梯不作為重連基準。

## 診斷與驗證

NetworkMonitor 記錄壅塞時的佇列、當次速率、EMA 及估算積壓時間。策略記錄事件、調整前後目標、設定上限與套用失敗。需由宿主 App 收集 HaishinKit logger，才能出現在現場日誌。

NetworkMonitorTests 涵蓋快速增長佇列、靜態後恢復、短暫尖峰、持續積壓、完全停滯與延遲採樣；StreamBitRateStrategyTests 補充冷卻恢復、待確認積壓、快速排空及重連階梯。

Windows 隔離測試使用原始監控與策略檔，僅替換 Apple 媒體型別與 logger。完整 Apple framework 編譯及 VideoToolbox 實機效果仍需 macOS/iOS 驗證。
